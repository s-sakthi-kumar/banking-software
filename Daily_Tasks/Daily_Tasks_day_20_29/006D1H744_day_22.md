### Task 1: What are Stereotype Annotations?

Stereotype annotations are **Spring annotations used to identify the role of a class** in the application. They tell Spring that the class should be managed as a **Spring Bean**.

Common stereotype annotations are:

* `@Component` – Generic Spring-managed component.
* `@Service` – Used for the **business/service layer**.
* `@Repository` – Used for the **data-access/DAO layer**.
* `@Controller` – Used for the **web/MVC controller layer**.
* `@RestController` – Used for REST APIs; combines `@Controller` and `@ResponseBody`.

---

### Task 2: Stereotype annotations used in Spring

For example, in a typical Spring application:

```java
@Repository
public class UserRepository {
    public User findUser(int id) {
        // Database operation
        return user;
    }
}
```

`@Repository` tells Spring that this class handles database operations.

```java
@Service
public class UserService {

    private final UserRepository repository;

    public UserService(UserRepository repository) {
        this.repository = repository;
    }

    public User getUser(int id) {
        return repository.findUser(id);
    }
}
```

`@Service` represents the business logic layer.

```java
@RestController
@RequestMapping("/users")
public class UserController {

    private final UserService service;

    public UserController(UserService service) {
        this.service = service;
    }

    @GetMapping("/{id}")
    public User getUser(@PathVariable int id) {
        return service.getUser(id);
    }
}
```

`@RestController` handles HTTP requests and returns the response directly, usually as JSON.

So the flow is generally:

**Controller → Service → Repository → Database**

### Task 3: Key concepts of JDBC connection

Some important JDBC concepts are:

1. **Driver / DriverManager** – JDBC uses a database driver to communicate with the database and establish a connection.

2. **Connection** – Represents the connection/session between the Java application and database.

3. **Statement / PreparedStatement** – Used to execute SQL queries. `PreparedStatement` is preferred because it supports parameters and helps prevent SQL injection.

4. **ResultSet** – Contains the data returned from a `SELECT` query and allows us to iterate through the results.

5. **Transaction** – Groups multiple database operations so they can either all succeed or all be rolled back.

In Spring JDBC, classes such as `JdbcTemplate` simplify much of this boilerplate.

---

### Task 4: Best practices when modernising an application with Spring JDBC

| Area                     | Two best practices                                                                                                                                                            |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Database connections** | Use `DataSource` and connection pooling instead of manually creating connections. <br> Let Spring manage connection lifecycle.                                                |
| **SQL queries**          | Use `PreparedStatement`/parameterized queries instead of string concatenation. <br> Keep SQL queries maintainable and avoid duplicating SQL throughout the application.       |
| **Transactions**         | Use Spring's `@Transactional` for transaction management. <br> Keep transactions short and avoid unnecessary database operations inside them.                                 |
| **Data access**          | Prefer `JdbcTemplate` or `NamedParameterJdbcTemplate` to reduce JDBC boilerplate. <br> Keep database logic inside repository/DAO classes rather than controllers or services. |
| **Performance**          | Use connection pooling and appropriate indexes. <br> Avoid unnecessary queries and use pagination for large datasets.                                                         |
| **Security**             | Never store database credentials directly in source code. <br> Use environment variables or secure configuration management for credentials.                                  |


### Task 5: How does Spring integrate with Hibernate or JPA, and what benefits does this bring?

Spring integrates with **JPA/Hibernate** through its ORM support, managing things like the `EntityManager`, transactions, and configuration.

For example:

```java
@Repository
public class UserRepository {

    @PersistenceContext
    private EntityManager entityManager;

    public User findById(Long id) {
        return entityManager.find(User.class, id);
    }
}
```

**Benefits:**

* Reduces boilerplate code for database operations.
* Provides dependency injection and easier configuration.
* Integrates ORM operations with Spring's transaction management.
* Makes it easier to switch between JPA providers such as Hibernate.

---

### Task 6: What is the role of `@PersistenceContext` in Spring ORM?

`@PersistenceContext` injects a **JPA `EntityManager`** into a Spring-managed class.

The `EntityManager` is responsible for operations such as:

```java
entityManager.persist(user);
entityManager.find(User.class, id);
entityManager.remove(user);
```

Spring manages the lifecycle of the `EntityManager` and associates it with the current transaction, so we don't need to manually create or close it.

### Task 7: How does Spring's transaction management improve ORM usage?

Spring provides declarative transaction management using `@Transactional`.

```java
@Transactional
public void transferMoney(Long from, Long to, double amount) {
    // debit account
    // credit account
}
```

**Benefits:**

* **Atomicity:** Multiple database operations succeed or fail together.
* **Rollback:** If an exception occurs, changes can automatically be rolled back.
* **Less boilerplate:** No need to manually call `begin()`, `commit()`, or `rollback()`.
* **Consistent ORM behavior:** Spring binds the persistence context/`EntityManager` to the transaction.

### Task 8: What is the role of `DispatcherServlet` in Spring MVC?

`DispatcherServlet` is the **front controller** of Spring MVC. It receives incoming HTTP requests and decides which controller should handle each request.

Typical flow:

**Client → DispatcherServlet → Controller → Service → DAO → Response**

It uses **HandlerMapping** to find the appropriate controller and then returns the controller's response to the client.

---

### Task 9: How does Spring MVC achieve separation of concerns between Controller, Service, and DAO layers?

Each layer has a specific responsibility:

* **Controller:** Handles HTTP requests, validates/request-maps input, and returns responses.
* **Service:** Contains the application's **business logic** and coordinates operations.
* **DAO/Repository:** Handles **database access** and persistence operations.

For example:

```text
UserController
      ↓
UserService
      ↓
UserRepository
      ↓
Database
```

### Task 10: Difference between `@RequestMapping` and `@GetMapping` / `@PostMapping`

`@RequestMapping` is a **general-purpose mapping annotation** that can handle different HTTP methods.

```java
@RequestMapping(value = "/users", method = RequestMethod.GET)
public List<User> getUsers() {
    // ...
}
```

`@GetMapping`, `@PostMapping`, `@PutMapping`, and `@DeleteMapping` are **specialized shortcuts** for specific HTTP methods.

```java
@GetMapping("/users")
public List<User> getUsers() {
    // ...
}

@PostMapping("/users")
public User createUser(@RequestBody User user) {
    // ...
}
```

<!-- So, **`@GetMapping` is essentially a more concise and readable way of writing a `@RequestMapping` specifically for GET requests.** -->
