### Task 1: ORM Concepts and JPA

ORM maps Java objects to relational database tables, allowing developers to work with objects instead of writing SQL for every operation. **JPA** is a Java specification that defines standard APIs and annotations for ORM, while Hibernate is one of its implementations.

### Task 2:Hibernate Fundamentals

Hibernate is a popular and powerful JPA implementation that provides automatic SQL generation, entity mapping, transactions, and caching. Its **first-level and optional second-level caches** reduce repeated database queries and improve application performance.

### Task 3: Entity Mapping and Relationships

**One-to-One, One-to-Many, and Many-to-Many** relationships define how entities are connected in the database. They affect table structure through foreign keys/join tables and can increase query complexity, especially for deeply nested or Many-to-Many relationships.

### Task 4: JPQL, Criteria API, and Native Queries

**JPQL** is readable and works with entities rather than tables, making it convenient for most queries. **Criteria API** is more flexible for dynamically building queries but is more verbose. **Native SQL** provides maximum database-specific flexibility and control but reduces portability.

### Task 5:Spring Data JPA Repositories

Spring Data JPA automatically provides repository implementations and supports methods such as `save()`, `findById()`, and derived queries like `findByEmail()`. However, relying heavily on derived methods can create long, complex method names and make complicated queries difficult to understand and maintain.

### Task 6: `LazyInitializationException`

`LazyInitializationException` usually occurs with **LAZY loading** when a lazy relationship is accessed after the Hibernate session/transaction has closed. **EAGER loading** normally avoids this because the related data is fetched while the entity is being loaded.


### Task 03 — Redis for SessionWhy is Redis preferred over traditional databases for session management in high-traffic web applications, and what risks arise if persistence is not configured?**
Redis stores sessions in memory, providing very fast read/write operations with low latency. It also supports TTL (expiration), making it easy to automatically remove expired sessions. If Redis persistence is not configured, a crash or restart can cause session data loss, potentially logging out many users simultaneously.

### What is a cache stampede, and how can techniques like request coalescing or probabilistic early expiration help prevent it?**
A cache stampede occurs when a popular cache entry expires and many requests simultaneously query the database to rebuild it. Request coalescing allows only one request to refresh the cache while others wait for the result. Probabilistic early expiration refreshes entries slightly before they expire, spreading database load over time.

### Why is it critical to apply the same migration scripts sequentially across Dev, Test, Staging, and Production, and what risks arise if environments drift?**
Using the same migrations ensures that every environment has the same database structure and version. If environments drift, applications may behave differently between testing and production. This can cause deployment failures, missing columns/tables, data corruption, or unexpected application errors.

### In what scenarios is a rollback preferable to a fix-forward approach, and how do tools like Liquibase and Flyway differ in supporting rollback strategies?**
Rollback is useful when a migration causes serious problems and the previous schema must be restored quickly. Fix-forward is often preferred when rolling back would risk data loss or when the change is already partially deployed. Liquibase provides explicit rollback support through rollback definitions, while Flyway primarily follows a versioned, forward-migration approach and has more limited rollback capabilities depending on its edition/features.

### How does the expand/contract pattern ensure application availability during schema evolution, and what are the trade-offs of delaying the contract phase?**
The expand phase adds new schema elements without removing the old ones, allowing old and new application versions to work together. After the application is migrated, the contract phase removes the old schema elements. Delaying the contract phase improves safety but leaves unused columns, tables, or compatibility code that increases schema complexity.

### What role does data validation (row counts, checksums, referential integrity) play in ETL-based migrations, and how can automation reduce human error?**
Validation confirms that data was transferred completely and accurately during migration. Row counts, checksums, and referential-integrity checks can detect missing, duplicated, or corrupted data. Automated validation scripts and migration pipelines reduce manual mistakes and make migration results repeatable.

### Why is datatype mapping a critical challenge when migrating between heterogeneous database engines, and how can mismatches impact application performance?**
Different databases represent data types differently, such as `BOOLEAN`, timestamps, numbers, and large text fields. Incorrect mapping can cause data truncation, precision loss, conversion errors, or inefficient storage. Poor datatype choices can also prevent indexes from being used effectively and reduce query performance.


### Beyond row count comparisons, what advanced techniques can be used to validate data integrity after migration, and why are application-level tests essential?**
Validation can include checksums/hashes, aggregate comparisons, foreign-key validation, uniqueness checks, sampling, and business-rule validation. Application-level tests are essential because technically correct data may still violate application-specific rules or workflows. These tests verify that the migrated system behaves correctly from the user's perspective.
