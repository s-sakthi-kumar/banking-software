
## Task 1: Codebase Practices

Consistent codebase practices are essential for keeping large enterprise applications scalable and maintainable.

* **Naming conventions** make code easier to understand and reduce the time developers spend figuring out what classes, methods, and variables represent.
* **Modularization** divides a large application into smaller, independent components. This makes it easier to develop, test, debug, and modify individual parts without affecting the entire system.
* **Version control discipline** ensures that changes are tracked, reviewed, and reversible. Practices such as meaningful commits, branching strategies, and pull requests reduce integration problems.
* **Consistent coding standards** make contributions from different teams look similar, reducing the learning curve for new developers.
* **Clear project structure** helps developers quickly locate functionality and prevents unrelated responsibilities from becoming tightly coupled.

Overall, these practices reduce technical debt and make it easier to **scale both the codebase and the development team**.

## Task 2: Communication

In a distributed microservices architecture, **asynchronous communication** is often preferred because the sender does not need to wait for the receiver to complete processing.

For example:

```text
Order Service
     |
     | OrderCreated event
     ↓
 Message Broker
     |
     ├──→ Payment Service
     ├──→ Inventory Service
     └──→ Notification Service
```

### Advantages

* **Loose coupling:** Services don't need to be directly available at the same time.
* **Better resilience:** Temporary failure of one service doesn't necessarily stop the sender.
* **Improved scalability:** Messages can be queued and processed by multiple consumers.
* **Better responsiveness:** The calling service can continue its work without waiting.

### Trade-offs

* **Eventual consistency:** Data may not be immediately consistent across services.
* **More complexity:** Message brokers, queues, retries, and consumers must be managed.
* **Debugging is harder:** Following a request across asynchronous events can be difficult.
* **Duplicate messages:** Consumers may need idempotency to safely process repeated messages.
* **Ordering issues:** Events may arrive out of order.

So, asynchronous communication improves **decoupling and resilience**, but introduces additional **distributed-system complexity**.

## Task 3: Data

The main difference is whether the application needs to preserve information between requests or whether the information exists only temporarily.

### Stateful data

Stateful systems maintain information about previous interactions.

For example:

```text
User logs in
    ↓
Session stored
    ↓
Next request uses that session
```

The server or another component must maintain the user's state.

**Advantages:**

* Useful for sessions, workflows, transactions, and long-running processes.
* Can make certain operations simpler because previous state is available.

**Disadvantages:**

* Scaling becomes harder because requests may need to reach the server holding the state.
* Failover becomes more complicated.
* State must be replicated or shared between instances.

### Stateless data

A stateless service does not depend on information stored in a particular application instance between requests.

For example:

```text
Request + Authentication Token
             ↓
        Any instance
             ↓
          Response
```

This makes **horizontal scaling** easier because any instance can handle any request.

**Advantages:**

* Easier load balancing.
* Easier failover.
* Easier horizontal scaling.
* Application instances can be replaced without losing local state.

**Disadvantages:**

* State may need to be stored in external systems such as databases, Redis, or object storage.
* Additional network/database access can affect performance.

In modern distributed systems, application services are often designed to be **stateless**, while persistent state is managed by dedicated data stores.

## Task 4: Fault Tolerance & Monitoring

Proactive monitoring and fault-tolerant design work together to prevent a small failure from becoming a system-wide outage.

Consider:

```text
Service A → Service B → Service C
```

If Service C becomes slow, Service B could keep waiting for it. Eventually Service B becomes overloaded, which affects Service A, potentially causing a **cascading failure**.

### Retries

Retries handle temporary failures.

```text
Request
   ↓
Failure
   ↓
Retry
   ↓
Success
```

However, retries should use **timeouts and exponential backoff**. Unlimited or immediate retries can actually make an outage worse.

### Circuit breaker

A circuit breaker stops repeatedly calling an unhealthy service.

```text
Healthy → Open after failures → Requests blocked
                         ↓
                    Try recovery
                         ↓
                      Healthy
```

This prevents failures from propagating to other services.

### Failover

If one instance or server fails, traffic can be redirected to another healthy instance.

### Monitoring

Monitoring detects problems such as:

* High latency
* Increased error rates
* CPU/memory exhaustion
* Failed requests
* Queue buildup
* Service health degradation

This allows teams to detect problems **before they become major outages**.

Therefore:

> **Monitoring detects failures early, while fault-tolerance mechanisms limit their impact.**

Together they improve the **availability, resilience, and stability** of a microservices ecosystem.
